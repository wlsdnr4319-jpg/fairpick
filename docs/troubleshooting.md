# 트러블슈팅 기록

개발하면서 실제로 겪은 문제를 증상 → 원인 → 해결 → 배운 점 순서로 적었습니다.

## 1. Windows 에서만 상세 API 가 500 에러

- **증상:** 일시(`prereg_end_at`, `verified_at`)가 있는 박람회만 500. 리눅스(Docker 이미지)에서는 생기지 않는 문제다.
- **원인:** `zoneinfo.ZoneInfo("Asia/Seoul")` 이 `ZoneInfoNotFoundError`. 리눅스는 OS 의 시간대 DB(`/usr/share/zoneinfo`)를 쓰지만 Windows 에는 없다.
- **해결:** `tzdata` 패키지를 의존성에 추가.
- **배운 점:** "내 PC 에서만" 생기는 에러는 OS 차이를 먼저 의심한다. 500 응답에는 원인을 숨기므로(보안), `raise_server_exceptions=True` 로 테스트를 다시 돌려 원인을 찾았다.

## 2. `alembic` 명령이 `UnicodeDecodeError: 'cp949'`

- **증상:** `alembic.ini` 에 한글 주석을 넣자 모든 alembic 명령이 실패.
- **원인:** Alembic 이 ini 파일을 OS 기본 인코딩으로 읽는다. 한국어 Windows 는 cp949.
- **해결:** `alembic.ini` 는 ASCII 로만 작성하고, 설명은 `env.py` 에 적었다.

## 3. 개발 DB 컨테이너가 뜨지 않음 (3306 포트)

- **증상:** `ports are not available: ... 0.0.0.0:3306 ... Only one usage of each socket address`
- **원인:** PC 에 설치된 MySQL80 서비스가 3306 을 쓰고 있었다. 처음 포트를 확인할 때 한글 Windows 의 `netstat` 은 `LISTENING` 대신 `수신 대기` 로 출력해 검색에 걸리지 않았다.
- **해결:** 개발용 컨테이너는 호스트 포트 3308 을 기본값으로 쓴다 (`DB_PORT` 로 변경 가능). 포트 확인은 `Get-NetTCPConnection -State Listen` 으로.

## 4. Nginx 보안 헤더가 페이지마다 다르게 붙음

- **증상:** `X-Frame-Options`, `X-Content-Type-Options` 가 API 응답에는 있는데 HTML·정적 파일에는 없다.
- **원인:** Nginx 는 `location` 블록 안에 `add_header` 가 하나라도 있으면 `server` 블록의 `add_header` 를 **전혀** 물려받지 않는다. `location /` 에 `add_header Cache-Control ...` 를 넣은 것이 원인.
- **해결:** location 의 캐시 설정을 `expires` 지시어로 바꿔 `add_header` 를 없앴다. 운영 구성을 로컬에서 띄워 `curl -I` 로 확인.

## 5. 전문 검색 테스트만 결과가 0건

- **증상:** `LIKE` 를 ngram FULLTEXT 로 바꾸자 검색 테스트가 실패. 개발 DB 에서 직접 검색하면 잘 된다.
- **원인:** InnoDB FULLTEXT 인덱스는 **커밋된 행만** 반영한다. 테스트는 각자 롤백되는 트랜잭션 안에서 데이터를 만들기 때문에 인덱스에 들어가지 않았다.
- **해결:** 전문 검색 테스트는 데이터를 실제로 커밋하고, 끝나면 지우는 fixture 를 따로 만들었다. 한 글자 검색어는 ngram 토큰(2글자)보다 짧아 `LIKE` 로 처리.

## 6. 로그인이 이유 없이 풀릴 수 있음 (설계 단계에서 발견)

- **증상(예상):** 새로고침 직후 또는 여러 요청이 동시에 만료되면 로그아웃된다.
- **원인:** 리프레시 토큰은 쓸 때마다 새로 발급하고, 폐기된 토큰이 다시 오면 탈취로 보고 전부 폐기한다. React StrictMode 는 개발 중 effect 를 두 번 실행하므로 `/auth/refresh` 가 같은 토큰으로 두 번 나가고, 두 번째 요청이 '재사용'으로 탐지된다.
- **해결:** 재발급 요청을 모듈 단위 Promise 하나로 묶었다(single-flight). 앱 시작 복구와 401 재시도가 같은 함수를 쓴다.

## 7. 기간 정규화의 '해 넘김' 규칙이 잘못된 입력도 통과

- **증상:** `"2026.11.22 ~ 2026.11.19"` 가 2026-11-22 ~ 2027-11-19 로 해석됐다.
- **원인:** "끝이 시작보다 빠르면 끝 연도 +1" 규칙을 끝 연도를 명시한 경우에도 적용했다.
- **해결:** 끝 연도를 생략했을 때(`"12.30 ~ 1.2"`)만 해 넘김으로 본다. 실패 케이스를 단위 테스트로 추가.

## 8. 킨텍스 홀 이름에 줄바꿈이 섞임

- **증상:** 장소가 `"킨텍스 전시홀 6C\n\t\t ,\n 전시홀 7"` 처럼 저장될 뻔했다.
- **원인:** 목록 HTML 이 홀마다 줄바꿈과 들여쓰기를 넣는다.
- **해결:** 공통 `clean_text()` 로 공백을 한 칸으로 줄이고 쉼표 앞 공백을 지운다. 저장한 HTML fixture 로 파서를 테스트해 재발을 막는다.

## 9. 분석 차트의 한글·가운뎃점이 깨짐

- **증상:** matplotlib 차트의 한글이 네모로, '문화·예술' 의 '·' 이 빈칸으로 나온다.
- **원인:** 기본 폰트에 한글이 없고, 맑은 고딕에는 가운뎃점(U+00B7) 글자가 없다.
- **해결:** `font.family = "Malgun Gothic"` 지정, 표시용 이름의 '·' 을 한글 가운뎃점 'ㆍ'(U+318D)로 바꿨다.

## 10. IP 기준 로그인 제한을 헤더 하나로 피할 수 있었음 (구현 중 발견)

- **증상(예상):** 공격자가 요청마다 `X-Forwarded-For: 1.2.3.<n>` 을 바꿔 보내면 IP 당 실패 횟수 제한에 걸리지 않는다.
- **원인:** Nginx 가 `$proxy_add_x_forwarded_for` 로 클라이언트가 보낸 값 뒤에 실제 IP 를 *덧붙였고*, uvicorn 은 `--forwarded-allow-ips "*"` 라 목록의 맨 앞(클라이언트가 쓴 값)을 접속 IP 로 썼다.
- **해결:** Nginx 가 맨 앞단이므로 `proxy_set_header X-Forwarded-For $remote_addr;` 로 덮어쓴다. 추가로 Nginx `limit_req` 로 인증 API 를 IP 당 분당 30회(순간 20회)로 제한하고, 넘으면 앱과 같은 JSON 에러 형식으로 429 를 준다. `nginx -t` 와 실제 요청으로 429 를 확인했다.

## 11. 수집 소스를 늘리며 만난 문제들

- **사이트마다 일정 화면이 다르다.** SETEC 은 목록형, 엑스코는 자바스크립트로 목록을 불러오지만 인쇄용 연간 일정표(`schedule_list.html`)는 정적 표, 수원메쎄·코엑스 마곡은 달력형만 있다. 코엑스 마곡의 다른 달은 `admin-ajax.php` POST 로만 받을 수 있어 수집 클라이언트에 `post()` 를 추가했다.
- **달력형은 같은 행사가 날짜 칸마다 반복된다.** 행사 ID 로 날짜를 모아 가장 이른 날 ~ 가장 늦은 날을 기간으로 만든다(`app/crawlers/calendar.py`). 달을 넘기는 행사(10.30 ~ 11.1)가 잘리지 않게 지난달 달력도 받고, 지난달에 이미 끝난 행사는 뺀다. 처음에는 이걸 빼지 않아 10월에 끝난 행사 12건이 검수 큐에 들어갔다.
- **코엑스 마곡 달력 칸에는 날짜가 일(日) 숫자뿐이다.** 칸은 달력 첫날부터 하루씩 이어지므로 순서로 날짜를 계산하고, 칸의 숫자와 다르면 `CalendarLayoutError` 로 수집 실패를 기록한다(구조가 바뀌었다는 신호, 2회 연속이면 관리자 메일).
- **엑스코 표에는 행사 번호가 없다.** 처음에는 '연도:행사명' 을 ID 로 썼는데 같은 해에 같은 이름의 웨딩박람회가 여러 번 열려 88건 중 81개만 고유했다. '개막일:행사명' 으로 바꿨다.
- **수집하지 않기로 한 곳.** aT센터는 Cloudflare 가 봇 요청을 403 으로 막고, 다른 도메인(at.or.kr)의 행사일정 경로는 robots.txt 가 금지한다. 벡스코는 robots.txt 가 메인 외 전체를 금지한다. 우회하지 않고 관리자가 직접 등록한다 (`seed_data.CRAWL_EXCLUDED`).

## 12. 카카오 로그인이 KOE205 로 실패할 수 있음 (구현 중 발견)

- **증상(예상):** 카카오 로그인 화면 대신 'KOE205 잘못된 요청' 이 뜬다.
- **원인:** `scope=profile_nickname account_email` 처럼 동의항목을 직접 요청했는데, 콘솔에서 그 항목(특히 이메일)을 설정하지 않았다. 이메일 항목은 앱 설정에 따라 켤 수 없는 경우도 있다.
- **해결:** 카카오는 scope 를 보내지 않는다. 그러면 콘솔에서 설정한 동의항목만 묻는다. 이메일을 못 받으면 이메일 없이 가입시키고 알림 메일만 건너뛴다. 구글은 `openid email profile` 을 그대로 요청한다.

## 13. 지난 행사 수집이 중간에 멈춤 (중복 키)

- **증상:** `backfill_archive` 가 엑스코 2019년에서 `Duplicate entry 'exco-2019-05-18:2019 웨딩쿨 웨딩박람회'` 로 멈췄다.
- **원인:** 원본 연간 일정표에 같은 행사가 두 줄로 적혀 있었다. 세션이 `autoflush=False` 라 같은 묶음 안에서 먼저 추가한 행을 조회로 찾지 못하고 두 번 INSERT 했다.
- **해결:** 저장 전에 묶음 안에서 `external_id` 로 한 번 합친다. 해마다 커밋하므로 다시 돌리면 이어서 저장된다. 테스트에 '원본의 중복 줄' 케이스를 추가했다.
- 같은 수집에서 SETEC 원본의 `2023-01-10 ~ 2022-12-11`(끝이 시작보다 빠른 오타)은 정규화 함수가 거부해 건너뛰었다.

## 14. 주제 키워드가 다른 낱말 속에 걸림 ('기타' 65% → 3%)

- **증상:** 지난 행사 2,233건 중 65%가 '기타'였다. 키워드를 늘리자 이번에는 '한국건축산업대전'이 식음료로, '인터내셔널 뷰티 아트페어'가 식음료로, '(사) 한국민화협회 회원전'이 산업으로 분류됐다.
- **원인:** 제목에 키워드가 '들어 있는지'로 판단해서, 짧은 키워드가 다른 낱말 속에서 걸렸다. '건축산업' 속 '축산', '뷰티아트' 속 '티아트', '회원전' 속 '원전'. 또 '기타' 대부분은 주제가 없던 게 아니라 일반 박람회가 아니었다(아파트 입주박람회 124건, 선거 개표·공연·면세점 행사, B2B 산업 전시·학술대회).
- **해결:**
  - 짧은 키워드는 더 긴 말로 좁혔다('축산박람회', '월드티아트', '원전생태계'). 회귀 테스트에 '이렇게 쓰면 이 제목이 잘못 간다' 사례를 한 줄씩 남겼다.
  - 규칙 순서를 우선순위로 썼다. 입주박람회 → 학술대회·상담회(B2B 확실) → 박람회 아님 → 일반인 주제 → '산업'·'기술' 같은 넓은 말. 그래서 '건강산업박람회'는 뷰티·건강으로, '미용의료기기 학술대회'는 산업·학술로 간다.
  - 입주박람회와 박람회가 아닌 행사는 통계 주제 표에서 빼고, 몇 건을 뺐는지 화면과 노트북에 적었다.
  - 바꾸기 전에 DB 를 건드리지 않고 새 규칙으로 전체를 다시 나눠, 원래 주제가 있던 행사 중 바뀐 것만 따로 확인했다(회귀 확인). 그 뒤 `backfill_archive --retheme` 으로 반영했다.

## 15. 새로고침하면 북마크가 풀린 것처럼 보임 / 로그인 후 홈으로 감 (E2E 로 발견)

- **증상 1:** 북마크한 박람회 상세에서 새로고침하면 '북마크 1명'인데 북마크 버튼은 안 눌린 상태였다.
- **원인 1:** 액세스 토큰은 메모리에만 있어서 새로고침하면 `/auth/refresh` 로 로그인을 복구한다. 그런데 화면은 복구를 기다리지 않고 바로 상세를 요청해, 토큰 없이(비로그인으로) 받은 `is_bookmarked: false` 가 캐시에 남았다. 복구 뒤에 다시 받는 코드가 없었다. 단위 테스트는 가짜 응답이 즉시 와서 순서 문제가 드러나지 않았다.
- **해결 1:** 로그인 복구가 성공하면 `queryClient.cancelQueries()` 로 진행 중인 요청을 취소한 뒤 `invalidateQueries()` 로 모든 쿼리를 다시 받는다. 복구가 끝날 때까지 화면 전체를 막는 방법도 있지만, 첫 화면이 늦어져서 고르지 않았다.
- **처음 고친 것이 CI 에서만 실패:** 처음에는 `invalidateQueries()` 만 했다. 로컬 E2E 는 통과했는데 CI 에서는 같은 증상이 남았다. CI 의 Playwright trace 에서 요청 순서를 보니 `GET /fairs/1`(토큰 없음)이 진행 중일 때 복구가 끝났고, 그 뒤 `/fairs/1` 을 다시 요청하지 않았다. TanStack Query 는 **아직 데이터가 없는 쿼리가 요청 중이면** 무효화해도 새로 요청하지 않고 진행 중인 요청을 그대로 쓴다(데이터가 있을 때만 취소 후 재요청). 로컬은 첫 응답이 복구보다 먼저 끝나서 드러나지 않았다. 이 순서(목록 요청 시작 → 복구 끝 → 토큰 없는 응답 도착)를 그대로 만드는 단위 테스트를 추가하고, 취소 없이는 실패하는 것을 확인했다.
- **증상 2:** 비로그인으로 북마크 → 로그인 화면(`/login?next=/fairs/1`) → 로그인하면 가끔 박람회가 아니라 홈으로 갔다.
- **원인 2:** 로그인 화면은 `GuestOnlyRoute`(로그인한 사람은 홈으로) 안에 있다. 로그인에 성공해 `user` 가 생기는 순간 가드가 다시 그려지며 홈으로 보내고, 로그인 화면은 그다음에 `navigate(next)` 를 부른다. 둘 중 어느 쪽이 마지막이냐에 따라 결과가 달랐다. 기존 단위 테스트는 가드 없이 로그인 화면만 그려서 놓쳤다.
- **해결 2:** 가드도 `safeNext(next)` 로 보낸다. 어느 쪽이 이겨도 같은 곳으로 간다. 단위 테스트도 앱과 같이 가드 안에 로그인 화면을 넣었다.
- 두 버그 모두 고치기 전 코드에서 실패하는 단위 테스트를 먼저 확인하고 고쳤다.

## 16. Vitest 에서 잡힌 에러가 테스트를 실패시킴

- **증상:** 위치 훅 테스트에서 '위치 실패' 를 흉내 내면, 훅이 에러를 잡아 화면에 문구까지 보여 줬는데도 테스트가 그 에러로 실패했다.
- **원인:** `beforeEach(() => vi.spyOn(...).mockResolvedValue(...))` 처럼 화살표 함수가 값을 바로 돌려주면, Vitest 는 돌려받은 함수를 '정리 함수'로 보고 테스트가 끝난 뒤 호출한다. 돌려준 값이 가짜 함수(spy)라 테스트 뒤에 한 번 더 불렸고, 그때 거부된 Promise 는 아무도 잡지 않았다.
- **해결:** `beforeEach(() => { vi.spyOn(...) })` 처럼 중괄호로 감싸 아무것도 돌려주지 않는다.

## 17. 페이지를 빨리 옮기면 로그아웃됨 (E2E 로 발견)

- **증상:** 관리자 E2E 가 모바일 화면에서 한 번, 수정 화면으로 이동한 직후 로그인 화면에 떨어졌다. 다시 돌리면 통과하는 '가끔' 실패였다.
- **원인:** Playwright trace 의 요청 순서: 새 페이지를 열 때 `/auth/refresh` 를 보냈고, 응답이 오기 전에 다음 페이지로 이동해 요청이 끊겼다(status -1). 서버는 이미 토큰을 회전(이전 토큰 폐기, 새 토큰 발급)했지만 브라우저는 새 쿠키를 받지 못해, 다음 페이지에서 **폐기된 이전 토큰**을 보냈다. 서버는 이를 탈취로 보고 모든 토큰을 폐기했다. 사용자도 링크를 빨리 누르면 똑같이 로그아웃될 수 있다. 같은 탭 안의 동시 재발급은 single-flight 로 막았지만, 페이지 이동으로 응답 자체가 사라지는 경우는 막을 수 없었다.
- **해결:** 회전할 때 '이 토큰 대신 발급한 토큰'(`replaced_by_id`)을 기록한다. 폐기된 토큰이 다시 와도 **회전 후 30초 안이고, 그때 발급한 토큰이 아직 살아 있으면** 응답을 못 받은 브라우저로 보고, 그 토큰을 폐기한 뒤 새로 발급한다. 로그아웃했거나 이미 탈취로 폐기됐다면 살아 있는 토큰이 없으므로 그대로 탈취로 처리한다. Auth0·Okta 의 refresh token reuse interval(grace period)과 같은 방식이다.
- **대가:** 토큰을 훔친 사람이 회전 직후 30초 안에 쓰면 탐지되지 않는다. 대신 정상 사용자가 로그아웃되지 않는다. 시간은 `REFRESH_REUSE_GRACE_SECONDS` 로 조정한다.
- 테스트: 유예 안 재사용 허용, 유예 후 재사용은 탈취, 로그아웃 뒤에는 유예 없음, 끊긴 뒤 받은 토큰으로 계속 재발급 가능.
